## 〇、第一轮结论更正

**Flash 模式并非配置冲突。** 第一轮报告将以下组合判定为 QIO 120MHz 未生效：

```text
CONFIG_ESPTOOLPY_FLASHMODE_QIO=y
CONFIG_ESPTOOLPY_FLASHMODE="dio"
CONFIG_ESPTOOLPY_FLASHFREQ_120M=y
CONFIG_ESPTOOLPY_FLASHFREQ="80m"
```

经核对 ESP-IDF v5.5.5 `components/esptool_py/Kconfig.projbuild:79-84, 93-97`：字符串值 `"dio"` 是 QIO 模式**镜像头**的派生值（bootloader 先以 DIO 启动，初始化后切四线模式）；`"80m"` 是 120MHz 目标频率的芯片启动阶段频率派生值。二者是生成镜像头所需，不代表运行期退化。**第一轮该结论错误，以本更正为准。** 微雪官方示例采用 QIO/PSRAM 80MHz，本项目 120MHz 仍需实机长期运行验证。

## 一、🔴 严重：登记流程可被抢先接管（且无撤销路径）

链条（逐环节核实）：`DESK_BRINGUP_DISPLAY_ON` 在 Kconfig **默认 `y`**（`components/board/Kconfig:14-19`）→ `app_main.c:624-628` 令 `allow_enrollment` 恒为 true → 设备无共享密钥时，任意连接者经 **Just Works 配对**（`sm_io_cap = BLE_SM_IO_CAP_NO_IO`、`sm_mitm = 0`，链路层无 MITM 保护）→ `ble_gap_security_initiate` 对**任何**连接者发起（`ble_link.c:365`）→ 登记密钥经该链路下发给对端（`app_auth.c:180-182`）→ 用同一把密钥验证 HMAC（只能证明"对端收到了刚发出的密钥"，验证不了身份）→ 密钥永久写入 NVS（`app_auth.c:213-229`），且协议 §3.1 的"清除绑定"入口**尚未实现，无撤销路径**。

- 后果：攻击者在设备首次开机、合法 Mac 之前完成"连接→配对→带登记标志的 HELLO→拿密钥→回 HMAC"，密钥即永久生效；合法 Mac 反而被锁死，且无法清除。
- 建议：① Kconfig 默认关闭 bring-up；② 登记必须配合人工确认（物理按键/屏幕弹窗）；③ 登记要求链路为 Authenticated 配对（如 Numeric Comparison）而非 Just Works；④ 提供已认证 Mac 发起撤销/重登记命令。

## 三、🟡 轻微项

**固件侧**
- 锁定时序：`app_main.c:81-106` 先清数据后禁触摸，架构文档要求"先禁触摸再清数据"——影响极小，改顺序或改文档。
- 认证超时从 CONNECT 起算（`app_main.c:768`）且超时不发 AUTH_RESULT；`MAC_SLEEPING` 事件无触发源（死事件）。
- status 特征无加密可读（`ble_link.c:234-246`，泄露版本/MTU/标志，低危）；分片发送失败可能泄漏 mbuf（`ble_link.c:609-620`，待 NimBLE 版本确认）。
- 断线重试无退避且 5 次耗尽后永久停连（`network.c:72-78`）；交易时段判断不含法定节假日（`market.c:38-49`）；RSSI 只在 GOT_IP 采集一次（`network.c:82-96`）；`DESK_MESSAGE_DEVICE_STATUS`(0x0010) 固件无发送路径。
- `http_fetch.c:73` PSRAM 分配无内部堆回退（与文档"优先 PSRAM"语义不符）；`http_fetch.c:99-108` 请求头设置返回值未检查；懒初始化理论竞态（`app_main.c:1033` 已显式 init，实际不触发）。
- `touch_reset` 直写 CH422G 输出寄存器绕过影子机制（`board.c:159-172`）——仅启动时调用，运行期重复调用会影子失步，建议注释约束。
- 诊断"运行时间"uint32 毫秒 49.7 天回绕（`app_main.c:52-55,863`）；启动期展示 mock 数据与真实诊断并存易误读（`app_main.c:955-956`）。
- 手势阈值代码 80（`app_main.c:1005`）与审计复核记录/设计文档 120 不一致，需确认是有意回退。
- 监督任务栈 7168B（cJSON + LVGL 调用）偏紧，实机观察 `uxTaskGetStackHighWaterMark`。
- 字形覆盖检查扫描范围不含 main/board 等组件（`verify-preflight.sh:28-31`），CJK 文案扩散会漏报。

**macOS 助手侧**
- 钥匙串建议 `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`（防锁屏读取与备份迁移复制）（`DeskAuthentication.swift:168`）。
- 密钥不一致无自动恢复路径（可能重连死锁，正是开发记录"绑定状态不一致"问题的根源）。

## 四、✅ 确认到位的实现

- **协议两端严格对称**：帧格式（魔数/版本/小端 type/seq/len）、CRC-16/CCITT-FALSE（0xFFFF/0x1021）、分片头 4 字节、重组 2 秒超时、最大帧 524——Swift（`DeskProtocol.swift`）与 C（`ble_protocol.c`）逐字节一致。
- **序号滑动窗口正确**：16 位回绕、乱序、32 窗口、移位无 UB（`ble_protocol.c:112-152`），测试覆盖回绕/乱序/重复/过旧，已在 `app_main.c:598` 接线。
- **分片重组边界严**：包长上限 244、`fragment_count==0`/`index>=count` 拒绝、fragment 0 重置、2s 超时（uint32 减法回绕安全）、`length+fragment_length≤524` 越界检查、整帧 CRC 校验后才投递（`ble_link.c:141-217`）。
- **JSON 严格校验**：`cJSON_ParseWithLengthOpts` + 尾随内容全消费检查、`json_read_u32` 范围+整数性双重校验、字段上限、未认证拒绝系统/AI/媒体/控制/配网（`app_main.c:193-238, 686-745`）。
- **深交所"有界字段提取"确如设计**：48KB 响应不建 cJSON 树，`"picupdata"` 截界 + 逐字节边界检查（`market_parser.c:207-283`）。
- **weather 解析器**：UTF-8 边界截断防半字（`qweather_parser.c:114-130`）、strtol 全消费校验、数值 clamp、预警取消过滤与最高级选择。
- **CH422G 影子寄存器 + 互斥锁 + `_Static_assert`**：位定义（bit1 GT911 复位/bit2 背光/bit3 LCD 复位/bit4 SD CS/bit5 USB）与官方一致，RMW 在锁内、写失败不更新影子（`board.c:26-41, 72-144`）。
- **存储架构符合设计**：32 项有界队列、每 8 条或 2 秒批量刷新、2MB 轮转、挂载失败 10 秒重试、不自动格式化、日志脱敏（私密内容替换为 `[private event omitted]`）。
- **http_fetch**：响应上限在回调层真实生效、系统证书包、全局互斥锁真正串行化 TLS 握手、失败保留上次有效状态。
- **认证卫生**：`esp_fill_random` 硬件随机数、恒时比较、HMAC 域分隔、成功/失败后会话材料（含 pending_key）清零（`app_auth.c`）。
- **隐私边界**：通知标题/正文、AI 提示词/回答/完整项目路径在协议两侧均不传输；Wi-Fi/天气凭据只在已认证链路发送且不落日志。
